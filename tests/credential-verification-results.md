# Local Opaque Credential Verification — Validation Results

**Project:** Enterprise AI Service Operations & Intelligence Platform  
**Scope:** The local, test-only credential resolver [`src/credential_auth.py`](../src/credential_auth.py) and the operator tool [`scripts/manage_test_credentials.py`](../scripts/manage_test_credentials.py), as described in [Authentication sequence §5.1](../docs/authentication-authorization-sequence.md#51-implemented-local-credential-resolver)  
**Governing decision:** [ADR-0005](../docs/adr/0005-server-verified-identity-and-tenant-authorization.md) (Accepted), credential and outcome rules  
**Observed result:** **58 of 58 credential tests passed:** 49 offline and 9 PostgreSQL-backed, with **0 failed and 0 skipped**. The full repository suite (**179 tests**: 97 offline, 82 PostgreSQL-backed) passed in three consecutive runs, and the 11 schema-integrity SQL checks passed.  
**Execution date:** 2026-11-15

This establishes **identity only**. No HTTP API, authorization policy, or tenant-isolation test exists, and the `401`/`403`/`500` values below are the statuses ADR-0005 assigns to each outcome, not HTTP responses.

### Secrets in logs and exceptions (offline, 2 tests, all PASS)

`test_logs_and_exceptions_contain_no_credential_or_digest` drives the verified, inactive, revoked, unknown, malformed, and dependency-failure paths, including a dependency error whose message contains the credential. Neither the raw credentials, their random parts, nor their digests appear in any log record, exception message, `repr`, argument tuple, or formatted traceback. The logs do contain the expected categories and the non-secret `credential_id`.

`test_secret_echoing_dependency_error_is_unreachable_through_chaining` confirms the authentication error has neither `__cause__` nor `__context__`, so the echoing dependency error cannot be reached through exception chaining.

### Operator tool (offline, 2 tests, all PASS)

`list` shows IDs, actors, and status but never digests or credentials. `rotate` prints the new credential once, which then resolves, and nothing secret is written to the store. `revoke` takes effect, and removing an unknown ID fails with exit code 1. `issue` refuses a non-local database URL before writing anything.

### Negative controls

To check that the tests can fail, the suite was run against seven deliberate mutations of `src/credential_auth.py`, each restored byte-for-byte afterwards (never committed):

| Mutation | Tests failed (of 58) |
|---|---|
| Revocation check removed | 7 |
| Inactive actors allowed | 4 |
| Database error returns a verified actor | 7 |
| Raw credential logged | 2 |
| Stale mapping used after the store breaks | 3 |
| Dependency error chained into the authentication error | 5 |
| Writer lock made non-exclusive | 2 |

### Defects found and fixed during this work

- **Exception chaining.** An independent security review noted that `raise … from None` still leaves the dependency exception in `__context__`. Errors are now raised outside the `except` blocks, and a test asserts the chain is empty.
- **Concurrent operator writes.** The read-modify-write cycle had no lock, so a revoke racing an issue could re-enable a revoked credential. Writers now take an exclusive lock file.
- **Windows lock contention.** The new concurrency test then failed intermittently (10 of 15 runs): Windows reports a lock file being deleted as `PermissionError`, not `FileExistsError`. After that fix, one further failure appeared in 25 runs and its error was not captured. A bounded retry for Windows sharing violations on `os.replace` was added. The lock and write-path tests then passed 40 of 40 repeated runs, and the full suite passed three consecutive runs. A residual Windows-specific intermittent failure cannot be ruled out.

### Identity schema and provisioning unaffected

`db/003_actor_identity_and_grants.sql`, `src/identity_provisioning.py`, and `tests/test_identity_grants.py` are unchanged; all 87 identity tests and the 11 schema-integrity checks passed again. The resolver only reads `actor.is_active`; it never reads or writes grants.

### Operator tool, end to end

Against `eaiso_dev` in the verification container, with the store in a temporary directory outside the repository and every printed credential redacted from the captured output:

- credentials were issued for the provisioned fictional provider engineer and the provider administrator;
- both resolved to the correct actors;
- rotation produced a new credential for the same actor, and the old credential was refused as `revoked`;
- `list` showed IDs and status only, and the store file contained no raw credential.

## Limitations

- **Identity, not authorization.** Nothing calls the resolver yet. No HTTP boundary, membership or permission check, or tenant-isolation test exists.
- **Local file store.** Anyone who can write the store file, or the database, controls which actor a credential names. Owner-only permissions apply on POSIX only, and the default path is relative to the working directory.
- **Stale locks.** A lock left by a killed operator run must be removed by hand.
- **No credential policy.** There is no expiry, rate limiting, lockout, credential-use audit trail, or production credential management (OIDC, SSO).
- **Bearer secrets.** Credentials are replayable by whoever holds them. Transport security belongs to the future HTTP boundary.
- **Identical 401s.** The future boundary must return the same `401` for every `Unauthenticated` reason. The reasons are for server-side logs only.
- **One environment.** All results come from one Windows machine and one PostgreSQL container. No load or long-running stress tests were run.
